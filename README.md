# Лабораторная работа №3

## Структура проекта

В рамках лабораторной работы реализована конкурентная структура данных Stack
 в двух вариантах: блокирующем (`synchronized`) и неблокирующем
(`lock-free`) на основе CAS. Выполнено тестирование корректности в
многопоточной среде и анализ производительности с использованием JMH.

- `src/main/java/ru/lazer/concurrent` — реализации стека
- `src/test/java/ru/lazer/concurrent` — тесты корректности и стресс‑тесты
- `src/main/java/ru/lazer/jmh` — JMH-бенчмарки

---

## Постановка задачи

Цель работы — спроектировать конкурентную структуру данных с минимальным
количеством блокировок потока исполнения, в идеале lock-free, и провести тестирование корректности и
производительности в многопоточной среде.


---

## Реализации

### 1) `SynchronizedStack<E>`

- Все операции (`push`, `pop`, `size`) защищены ключевым словом `synchronized`.
- Корректность обеспечивается взаимным исключением и happens-before
  отношениями между потоками.
- Недостаток: при высокой конкуренции потоки блокируются на мониторе,
  что снижает масштабируемость.

### 2) `LockFreeStack<E>` (Treiber stack)

- Реализован lock-free стек на основе `AtomicReference` и CAS-циклов.
- Отсутствуют блокировки и ожидание монитора.
- Гарантия lock-free: если поток не может завершить операцию, значит
  прогресс делает другой поток.
- ABA-защита не используется, так как узлы не реиспользуются и управляются GC.

---

## Связь с Java Memory Model

- `synchronized` обеспечивает happens-before между выходом и входом в монитор,
  гарантируя видимость изменений.
- `compareAndSet` у `AtomicReference` имеет volatile-семантику:
  успешный CAS публикует изменения, а чтение головы имеет acquire-семантику.
- Это гарантирует корректную публикацию узлов между потоками без блокировок.

---

## Тестирование корректности

Проверяется:
- корректность LIFO-семантики в однопоточном режиме;
- отсутствие потерь и дубликатов элементов в многопоточном режиме;
- завершение работы без deadlock.

Запуск тестов:
```bash
mvn clean test
```

---

## Бенчмарки и производительность (JMH)

Для анализа производительности использован фреймворк **JMH** в режиме
`AverageTime`, измеряющем среднее время выполнения операции.

Бенчмарк:
- `pushPop` — последовательный вызов `push` и `pop` на общей структуре
  при конкурентном доступе нескольких потоков.

Запуск:
```bash
mvn clean package
java -jar target/benchmarks.jar StackJmhBenchmark -t 8
```

## Анализ результатов

Полученные результаты показывают, что в данном сценарии `push+pop` \версия на `synchronized` демонстрирует меньшую задержку,
чем lock-free реализация. 

Это объясняется тем, что:
- lock-free стек активно использует CAS-циклы, которые при сильном contention
  приводят к большому числу неуспешных CAS и росту затрат CPU;
- `synchronized` в современных JVM эффективно оптимизируется (lightweight locking)
  и при короткой критической секции может показывать лучшие результаты.

Таким образом, lock-free реализация не всегда гарантирует выигрыш по времени,
особенно при высокой конкуренции и коротких операциях.

---

## Вывод

В ходе лабораторной работы реализованы и исследованы две конкурентные версии
структуры данных Stack: блокирующая (`synchronized`) и неблокирующая (`lock-free`).
Экспериментально показано, что lock-free подход снижает блокировки, но может
уступать блокирующему решению по производительности в сценариях с высоким
уровнем конкуренции.
